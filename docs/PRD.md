## 1. 背景与问题

鸣潮玩家关心自己的抽卡运气：保底垫了多少、歪没歪、平均多少抽出金。但：

- 游戏内唤取记录只有流水列表，无任何统计，且官方仅保留**约 6 个月**记录；
- 社区网页版工具需要用户自行跑脚本导出，或依赖在线服务处理数据；
- 官方接口无公开文档，鉴权链接提取（客户端日志 XOR 混淆）有技术门槛。

本项目做一个**纯本地**的 Windows 桌面应用：一键从客户端日志提取官方唤取链接、拉取全量记录、本地永久保存，并以统计 + 趣味评价的方式展示用户的欧非情况。

## 2. 产品目标与成功标准

| # | 目标 | V1 验收口径 |
|---|---|---|
| G1 | 一键获取：玩家只要在游戏内打开过唤取记录页，无需看教程即可导入 | 全新 Windows 11 机器上，国服 + 国际服各实测一次一键获取成功 |
| G2 | 欧非一屏叙事：打开即见评语、五星编年史与保底倒计时 | 主画面首屏承载评语行、五星编年史名册与保底引线 |
| G3 | 隐私零上传：统计与存储全部本地 | 除官方 API 域名白名单外无任何网络请求（抓包验证） |
| G4 | 轻量：在意包体积 | 便携版 zip ≤ 15MB，解压即可运行 |
| G5 | 数据不丢：官方 6 个月窗口之外的历史仍可用 | 本地合并去重后记录只增不减，支持 JSON 备份/恢复 |

**V1 定位**：单机单人使用的「先做出来看看」版本，跑通「获取 → 存储 → 统计 → 展示」完整闭环。

## 3. 用户与场景

**用户画像**：鸣潮 PC 玩家（国服或国际服，含 Steam/Epic 渠道），单人或亲友共用电脑多号，懂基本电脑操作，不要求懂脚本。

| 场景 | 描述 | 产品应对 |
|---|---|---|
| 首次导入 | 装好软件，想马上看到统计 | 一键获取；失败时给出分步引导（含「先去游戏里打开唤取记录页」这一前置条件） |
| 日常更新 | 刚抽完卡想看欧非 | 一键刷新；提示「新记录约 30 分钟后可查」避免误判为 bug |
| 链接失效 | record_id 过期，拉取报错 | 明确提示 + 引导重新打开游戏唤取记录页后重试 |
| 多号/换号 | 日志里有多个 UID | 检出多个 UID 时弹选择；切换档案需确认 |
| 数据安全 | 换机/重装 | JSON 备份导出/导入 |

## 4. 功能需求

### F1 唤取记录获取

**F1.1 一键获取（首选入口）**

1. 自动发现游戏安装目录，优先级：注册表 Uninstall 项 → MuiCache → 防火墙规则 → Xbox `.GamingRoot` → 常见路径扫描（官方启动器 / WeGame / Steam / Epic）→ 手动指定目录（记住选择）。
2. 读取两处日志（相对安装根目录）：`Client\Saved\Logs\Client.log`（首选；有 XOR 混淆，按「先原文匹配、失败再解码（奇字节 ^0xA5 / 偶字节 ^0xEF）」双路径处理；以共享读方式打开以兼容游戏运行中）与 `Client\Binaries\Win64\ThirdParty\KrPcSdk_Global\KRSDKRes\KRSDKWebView\debug.log`（明文 JSON）。
3. 用社区通用正则提取唤取 URL，取最新一条；解析 9 个参数（svr_id / player_id / lang / gacha_id / gacha_type / svr_area / record_id / resources_id / platform），按 host 或 svr_area 判国服/国际服。
4. 遇到的典型故障要在 UI 有可读诊断：找不到安装目录、日志无 URL（未打开过唤取页）、日志被 `Engine.ini` 关闭、文件只读 ACL。

验收：国服 + 国际服各实测通过；游戏运行中可读取；日志混淆双路径均工作。

**F1.2 手动粘贴（兜底入口）**

用户粘贴唤取 URL（从日志或他人教程获得），与一键获取共用同一条拉取管线；校验 URL 格式与域名合法性后才使用。

**F1.3 记录拉取**

- 对每个卡池 code（1..=13，开放式枚举，未知 code 以「未知池」兜底）向官方 API 各发一次 `POST /gacha/record/query`（国服 `gmserver-api.aki-game2.com`，国际服 `.net`；请求体与头见调研汇报 §2.1，带对应 Referer）。
- **无分页**：每池一次请求返回该池全量历史（时间倒序）。
- 限速与容错：逐池串行、相邻请求间隔默认 1s（≥600ms）；单请求超时 15s；失败重试 3 次（间隔 1s）；`code != 0` 一律判定为链接失效，停止本次拉取并进入失效引导，不当作网络错误无限重试。
- 进度反馈：显示「正在获取 卡池 x/13」。

**F1.4 合并与去重**

- 去重键：`time + name + qualityLevel + 卡池 code`（API 记录无唯一 ID）。
- 合并策略：新拉取的池数据与本地按去重键合并，只增不删；官方 6 个月窗口外的旧记录永久保留在本地。
- 写库事务化：拉取中途失败/崩溃不产生半写状态。

**F1.5 多 UID**

- 提取 URL 时按 player_id 建映射而非只取第一条；检出多个 UID 时让用户选择要导入的档案。
- 检测到与当前档案不同的 UID：弹确认「切换档案（旧档案数据保留为只读历史）」。

### F2 统计展示（单画面编年史 + 抽屉/弹窗，见 ADR-0003、ADR-0007）

**F2.1 编年史主画面（产品门面）**

- 顶部池切换（角色精准调谐 / 武器精准调谐 / 常驻调谐 / 新手·感恩 四类页签）+ 一行汇总指标（总唤取、五星数、平均出货、歪率）。页签为**类别**：同一类别下若有多个卡池 code 的数据（如角色系限定 1/8/10/12），页签内提供二级池切换，统计与保底一律按具体 code 计算；出现未知 code 数据时动态追加「未知池」兜底页签（浅统计）。
- **五星编年史名册**：以时间倒序的角色卡片网格呈现全部五星（最新在最前）。每卡含**头像位**（42px；正式版按 resourceId 从本地资源包加载角色头像/武器图标，缺图时回退为属性色菱形水印 + 名字首字的字牌）、角色名、属性/武器类型小标、出货抽数（大号数字 + 0–80 微型进度条）、歪/UP 徽章、日期。**视觉三层编码（状态优先，配色定稿见 ADR-0006）**：①结局为第一层——UP = 主题强调色调底色 + 同色顶边 + 实心徽章（明色主题为共鸣青、暗色主题为低饱和金），歪 = 冷灰调底色 + 灰顶边 + 灰徽章（歪卡角色名转灰）；②欧非程度为第二层——出货数字与微型进度条着色，绿色 = 超欧（≤20 抽）、红色 = 超非（≥70 抽）、中性 = 正常；③属性/武器类型为第三层——头像旁小色点 + 文字。名册头部含汇总芯片（UP n · 歪 n · 超欧 n · 超非 n），一眼给出全局结论。首位为虚线「进行中」卡（强调色系，当前垫抽数 + 距必得剩余）。网格自动换行 + 内部滚动，规模可扩展至 50+ 条记录（虚拟化按需）；卡片可点击/键盘选中，下方详情条展示该五星完整信息；
- 欧非评语压缩为名册上方单行（评级字母 + 评语 + 平均出货 + 歪率）；
- **高光时刻纪念牌**：旅途总览（总抽数/五星数）、最欧（出手如电）、最非（漫长等待）、大保底就绪状态。

**F2.2 保底引线**

角色精准调谐 / 武器精准调谐 / 角色常驻调谐三条引线式倒计时：「距必得五星 N 抽」大数字 + 0–80 刻度尺；角色系限定池标注当前处于小保底 / 大保底。

**F2.3 记录抽屉**

顶栏「记录」按钮呼出右侧抽屉（不离开主画面）：

- 全量流水（时间倒序），列：时间、池、物品、稀有度（3/4/5 星着色）；
- 按池筛选、按稀有度筛选；空状态给「清除筛选」引导；
- 数据量保护：虚拟滚动，2 万条记录滚动流畅。

**F2.4 设置弹窗**

顶栏齿轮呼出：主题明暗切换（**明色默认**，与游戏内界面同源，见 ADR-0004；暗色为夜晚模式）、启动自动同步开关、安装目录探测/指定、导出备份/导入恢复/清空数据（二次确认）、关于与本地隐私声明。

### F3 欧非评价

**指标**（口径见 §5）：角色系限定池五星平均出货抽数（主指标）、歪率（修正项）。

**评语**：本地规则模板，不调用任何在线服务。评语档位同时映射为**欧非评级字母（S / A / B+ / B / C / D，与原型定稿一致）**，以 34px 菱形印章形式常驻编年史主画面评语行（视觉规范见 docs/design/DESIGN-SYSTEM.md）。V1 分档（文案实现时可润色）：

| 评级字母 | 平均出货抽数（角色系限定池） | 评语档位（示例） |
|---|---|---|
| S | ≤ 35 | 天选之人 |
| A | ≤ 50 | 欧洲常驻居民 |
| B+ | ≤ 62 | 手气不错 |
| B | ≤ 70 | 中规中矩 |
| C | ≤ 78 | 玄不救非 |
| D | > 78 | 保底战神 |

修正项：歪率 ≥ 80% 追加「命运的反面宠儿」；出过 ≤ 10 抽五星追加「十里坡剑圣」式彩蛋文案。样本不足（角色系限定池五星 < 2 个）时评语显示「样本不足，多抽点再来」。新手·感恩池不计入欧非总评：评级位置显示「—」，评语固定为「启程之人」（原型定稿）。

### F4 数据管理

- 存储：本地 SQLite（单文件，随档案）；
- 备份/恢复：导出 JSON（全部记录 + 档案元信息）、导入恢复（同一去重键规则合并）；往返一致；
- 清空数据：需二次确认。

不再单独成页，见 F2.4。

## 5. 统计口径（V1）

| 指标 | 定义 | 口径说明 |
|---|---|---|
| 出货抽数 | 取得一个五星所消耗的抽数（含出货那抽） | 按池内时间正序计算；池内最早记录若直接是五星，出货抽数按 1 计（本地无更早历史，界面标注「不完整」） |
| 歪 / 不歪 | 角色系限定池中，五星在**常驻名单**内 = 歪；名单外 = 当期 UP | 见 [ADR-0002](./adr/0002-standard-roster-off-banner-detection.md)；武器系限定池不适用（必中 UP） |
| 歪率 | 角色系限定池 歪的五星数 / 五星总数 | 仅角色系限定池计算 |
| 保底进度 | 当前池距上一个五星的抽数 | 距 80 硬保底的剩余；池 5（新手调谐）按 50 |
| 大小保底状态 | 上一个角色系限定池五星是否歪 | 歪 → 当前为大保底（下个五星必 UP） |
| 期望参考线 | 五星平均出货抽数对照的理论期望常量 | 角色系 62 抽（社区口径）；武器系 V1 暂不显示参考线（原型定稿）；界面标注「社区口径，仅供参考」 |
| 四星 | 仅计数展示 | 四星欧非分析 V2 |

**常驻名单**：初始随应用内置（角色系常驻五星清单），做成独立数据文件随版本更新；界面上未知物品（不在名单也不可判定）按「未知」标记不计入歪率。

## 6. 数据来源与技术事实（摘要）

完整调研（含来源 URL）：[docs/research-2026-09-25-gacha-api.md](./research-2026-09-25-gacha-api.md)。要点：

- 唤取 URL 只能从客户端日志提取，前置条件是玩家在游戏内打开过唤取记录页；Client.log 新版有 XOR 混淆；
- API 无分页、无签名，鉴权在 record_id 且会过期（`code != 0` 即失效，不假定固定有效期）；
- 官方仅保留约 6 个月记录、新记录约 30 分钟延迟 → 本地合并是硬需求；
- 国服/国际服仅域名差异；一份日志可能含多 UID。

**风险与应对**：

| 风险 | 应对 |
|---|---|
| 官方变更日志混淆/接口形态（有「3.4 加密」传闻，未确认） | 获取层独立成模块；「原文→解码」双路径；失败给手动粘贴兜底 |
| 依赖非公开接口，可能失效 | 不做任何「绕过」行为，仅读取本人数据；接口变更时发版修复 |
| time 字段时区语义未确认 | V1 按字符串原样排序展示，不做时区换算 |
| 大记录量（单池上千、总量上万） | SQLite + 虚拟滚动 + 指标计算缓存 |

## 7. 非功能需求

- **隐私**：所有统计本地完成；网络请求仅限官方 API 域名白名单（`gmserver-api.aki-game2.com/.net`）；无埋点、无崩溃上报、无自动更新检查（V1）。
- **无登录**：应用无账号体系，「档案」即一个 UID 的本地数据槽。
- **平台**：Windows 10/11 x64；开发在 macOS（Tauri dev），发布构建在 Windows 机 `tauri build`。
- **体积**：便携版 zip ≤ 15MB（Tauri 2 预期 ~10MB），解压即用、无需安装。
- **性能**：1 万条记录下，页签切换 < 200ms、指标计算 < 500ms；2 万条记录流水虚拟滚动流畅。
- **健壮性**：写库事务化，崩溃不丢不脏；断网时除获取外全部功能可用。
- **可用性**：暗/明主题均满足对比度要求；简体中文。

## 8. 技术方案概要

已定（[ADR-0001](./adr/0001-tauri-2-desktop-shell.md)）：**Tauri 2 + TypeScript 前端**，Rust 面最小化。

- 前端（§9 A1）：Vue 3 + TypeScript + Pinia，**不引入图表库**——编年史名册、微型进度条与保底刻度均为 CSS 实现（原型已验证，见 ADR-0007）；
- Rust 侧仅提供：安装目录探测、日志读取（共享读 + XOR 解码）、（经由官方插件）自定义 Referer/UA 的 HTTP 请求、SQLite（tauri-plugin-sql 或 rusqlite command）；
- 业务逻辑（拉取编排、限速重试、合并去重、统计口径、评语）全部在前端 TS，便于测试与迭代；
- 数据模型：记录表以 `player_id` 为档案键、去重键建唯一索引；常驻名单为随应用分发的数据文件。

## 10. 里程碑

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 数据链路 | 目录探测 → 日志读取/解码 → URL 解析 → 拉取（限速/重试）→ SQLite 落库合并 | 真实国服账号完整拉取并二次增量无重复；可用简易调试页验证 |
